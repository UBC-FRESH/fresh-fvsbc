- P2.2 smoke run. The built BC variant was installed into the spike environment and driven through PyFVS's step API on a bare-ground keyword file adapted from the `pn` fixture, with BC's `FD` species code and without the US `VOLEQNUM`. `init_projection`, `grow` for 20 cycles, and `end_projection` all return cleanly, and `f.summary` gives a coherent 200-year trajectory: trees per acre 173 falling to 90 through self-thinning, top height 9 to 142 feet, basal area 1 to 297, crown closure 3 to 223, and total cubic volume 0 to 13,108. **Merchantable cubic volume stays 0 for all 200 years** — root-caused and fixed. `common/ARRAYS.F77` states that `MCFV` holds "merchantable cubic foot volume per tree calculated in `VOLS`", and `base/gradd.f` builds `OMCCUR` from it. BC's `vols.f` never set `MCFV`; the US variants migrated to it (`ie/vols.f` shows `! WK1(I)=VM` replaced by `MCFV(I)=MCF`), and BC was left behind on the old array. Two lines in `canada/bc/vols.f` fix it: `mcuft` is now nonzero in 17 of 21 rows, reaching 12,751 against a total cubic of 13,108, matching the accumulated `SPCMC` exactly. Four hypotheses were disproved on the way, three of them mine: the summary-label theory, the `METHC=4` theory, the geometry alarm (`min.f`'s debug labels are wrong, not its values), and the `SPCMC`-not-accumulating theory (`IPASS=1` on all 2,850 calls). `mbdft` stays 0 by design: "Board feet not computed in this variant". Evidence in `notes/reference/fvsbc-smoke-run.md`.
- P2.2 validation against the official test suite. The FVS source ships an official BC oracle at `fvs/tests/FVSbc/` — keyword files, expected summaries, input databases, and expected database dumps — and it now runs. Three defects stood in the way, all fixed. **The `TreeSQL` path segfaulted**: the source list compiled the metric `INTREE`, which calls `DBSTREESIN` with 30 arguments, against the base `DBSTREESIN`, which expects 33, so the callee wrote through three argument slots that did not exist. One source-list line fixes it. **That file had never compiled**: `metric/dbsqlite/dbstreesin.f` used FVS's own preprocessor style (`# IF` with a space) where every sibling uses cpp style, so its three directives were normalized. **Every event-monitor expression failed**: `metric/base/evldx.f` accepted parameter references only up to `PARMS(5999)` while `common/OPCOM.F77` sets `MAXPRM=7999`, so the `COMPUTE` keyword and every `IF` block raised `FVS21` and the official keyword files' harvest-and-replant logic never fired; widening the range check to match `MAXPRM` removes all 320 error rows. Two smaller alignments with Ontario — `rd/rdin.f` and `rd/rdsout.f` to their metric twins — and a speculative `isstag.f` swap reverted. Result: **`FVS_Compute` matches the oracle exactly, 40 of 40 rows for stand 101**, and the summary's first row matches byte for byte, which independently confirms the database read, the tree decode, the metric units, and the column order. Not settled: the summary table's period rows still report `Year = 0` and `Age = 0` with wrong cubic columns, since the projection itself is now exact the fault is in the summary assembly; soft down woody debris differs; and only one of the four stands ran. Evidence in `notes/reference/fvsbc-validation.md`.
- P2.2 validation, continued: the numbers now match the oracle. Two more defects fixed. **The summary read `IOSUM` with the wrong stride**: `common/OUTCOM.F77` declares `IOSUM(22,MAXCY1)` and `metric/vbase/sumout.f` takes the leading dimension as an argument, but `metric/vbase/disply.f` passed 20 where `vbase/disply.f` passes 22, so the metric variant indexed a stride-22 array with stride 20 — which is why the initial summary row was correct and every later row was garbage. **Newly established trees inherited a dead tree's merchantable volume**: `metric/strp/estab.f` and `metric/strp/esuckr.f` reset `CFV` for a new tree but not `MCFV`, so newly planted trees carried the previous occupant's volume into `OMCCUR` before `vols.f` reached them; this showed up as `MCuM` with `TCuM = 0` at the rotation resets. That is the fourth instance of one pattern in this variant — a newer per-tree array introduced, and one of the sites that initialises the older arrays never updated — and it confirms the `vols.f` `MCFV` work in the smoke run, which now reproduces all nine of the oracle's nonzero merchantable-volume rows value for value. Result: **the fixed-width summary matches the official `StandStructure.sum.save` with zero differences across all 41 rows of stand 101**, and `FVS_Compute` remains exact at 40/40. The patch set is 8 modified files plus one new file, 19 insertions and 8 deletions, with the upstream CRLF line endings preserved. Still open: soft down woody debris, and only one of the four stands runs (a harness limit). Evidence in `notes/reference/fvsbc-validation.md`.
- P2.2 validation: **the first official case passes, using the FVS project's own command.** The blocker for running all four stands was the harness, not the variant: PyFVS's `init_projection` calls `filclose()` and then `INITRE`, so it always restarts at the top of the keyword file and the step API is single-stand by design. The FFI does expose the native `fvs` routine, one `PROCESS` per call, so the real driver's loop can be reproduced directly — `while int(f.fvslib.fvs()) == 0: pass` — which yields the oracle's `-999` headers exactly, `41 101 / 41 103 / 41 251 / 41 253`, and one `FVS_Cases` row per stand. With that, `grep -v -- "-999" StandStructure.sum | diff -w - StandStructure.sum.save` from `tests/FVSbc/makefile` exits 0 with zero differing lines across all 164 rows and four stands, and the run writes no error rows. `FVS_Compute` matches the dump exactly at 40 of 40 rows. The second case, `YSM-SkyRanch`, now also runs all fifteen stands — 375 rows, the oracle's length, no error rows — and 328 of 375 rows are identical, with twelve of fifteen blocks exact; the three that differ are `SkyRanch-Control`, `SkyRanch-1.0m`, and `SkyRanch-2.0m`, differing by small amounts across the aggregate columns (`Tph` by up to 30, `TopHt` by 2, `SDI` by 3), which points at a slightly different tree population appearing from 2054 rather than a formatting fault. - P2.2 narrowed the `YSM-SkyRanch` deviation. Of the five tables the official dump asserts, four now match exactly and one is short: `FVS_DM_Stnd_Sum_Metric` has 15 rows where the oracle has 375, one per stand rather than one per stand per report period, all dated to the initial year. The mechanism is exact: `metric/dbsqlite/dbsmis.f`'s `DBSMIS2` returns early when `IDM2` is zero and clears `IDM2` on three failure paths, and instrumenting them shows the third firing on the first call for every stand — the routine's `fsql3_exec(IOutDBref,"Commit;")` returns 1, after which the routine disables itself for the rest of the run. The insert is well formed and the same `Commit` succeeds in `DBSMIS1` and `DBSMIS3` in the same call sequence. Output-only, so it cannot explain the growth differences in the three SkyRanch blocks; next step is the SQLite error message at that call. The instrumented build was reverted and the first official case re-confirmed at zero differing lines.
- P2.2 fixed the under-written DM table. `metric/dbsqlite/dbsmis.f`'s `DBSMIS2` is the only one of the four `DBSMIS*` routines that issues a `Commit;` without a preceding `Begin;`, so its commit fails with "cannot commit - no transaction is active"; the routine treats that as fatal, clears `IDM2`, and never writes again — which is why `FVS_DM_Stnd_Sum_Metric` held one row per stand instead of one per stand per report period. Adding the missing `Begin;` takes it from 15 rows to the oracle's 375. With that, all five tables the official YSM-SkyRanch dump asserts now have the oracle's shape, and row content matches 15/15, 336/400, 311/375, 1431/1875, and 322/375. The `DM_Spp`, `DM_Stnd`, and `Summary` residuals sit entirely in the three SkyRanch stands already known to diverge; the `DM_Sz` residual touches all fifteen stands and is new and unexplained. The patch set is now nine modified files plus one new file, twenty insertions against eight deletions, re-exported and re-verified to apply cleanly to `ef5fa84` and reproduce the working tree byte for byte.
