# The BC tree list and its species codes

Facts about what fixes the FVS-BC tree-list input and its species codes, recorded while working `P2.1`
(#11). They correct two earlier claims in this project, both of which were wrong.

Date: 2026-10-21
Issues: #11
Read at: `forest-modeling/ForestVegetationSimulator`, branch `pyfvs-features`, commit `ef5fa84`

## How these facts were established

A sparse clone of the pinned branch, so the files could be read and grepped directly rather than through
the web interface:

```bash
git clone --depth 1 --filter=blob:none --sparse -b pyfvs-features \
    https://github.com/forest-modeling/ForestVegetationSimulator.git
git sparse-checkout set canada base common vbase bin
```

Every claim below cites a file and a line in that checkout.

## Correction 1: `BC.trf` is not a tree-list format

`canada/bc/BC.trf` is a Stand Visualization System plant-form asset. Its own header says so:

```text
;Stand Visualization System
;Plant form definition file
;File produced by SVS version: 3.10
;DO NOT EDIT THIS FILE BY HAND!!!!!
```

It has no bearing on the tree-list contract.

## Correction 2: `bcspp.f` is dead code

An earlier correction to this note named `canada/bc/bcspp.f` as the species table. That was wrong too.

- `bcspp.f` is **not in the BC build**. `grep bcspp bin/FVSbc_sourceList.txt` returns nothing, and the
  `canada/bc/` files that the source list does name are: `BCPLOT.F77`, `ESHAP.F77`, `ESPARM.F77`,
  `PRGPRM.F77`, `becset.f`, `blkdat.f`, `bratio.f`, `ccfcal.f`, `cfvol.f`, `cratet.f`, `crown.f`, `dgdriv.f`,
  `dgf.f`, `dubscr.f`, `forkod.f`, `grincr.f`, `grinit.f`, `grohed.f`, `habtyp.f`, `htgf.f`, `initre.f`,
  `keyopn.f`, `log.f`, `min.f`, `morts.f`, `natcrz.f`, `r6crwd.f`, `regent.f`, `revise.f`, `sitset.f`,
  `spctrn.f`, `varget.f`, `varput.f`, `vols.f`.
- `BCSPP` is **never called**. `grep -rn BCSPP` over `canada/`, `base/`, `common/`, and `vbase/` returns only
  the subroutine's own definition line.
- Its four variant branches (`IB `, `PN`, `WC`, `AK`) and their index ranges therefore have no effect on
  FVS-BC.

## The BC tree-record format

`canada/bc/blkdat.f`, lines 37 to 39, in a `BLOCK DATA BLKDAT` that the BC source list does compile:

```fortran
      DATA TREFMT /
     >'(I4,T1,I7,F6.0,I1,A3,F5.1,F4.1,2F5.1,F5.1,I1,3(I2,I2),2I1,I2,2I3,
     >2I1,F3.0)' /
```

`TREFMT` is the variant's default tree-record format. Note the species field: **`A3`**, three characters.

## The BC species codes

`canada/bc/blkdat.f`, lines 74 to 76:

```fortran
      DATA JSP /'PW ','LW ','FD ','BG ','HW ','CW ','PL ','SE ',
     &  'BL ','PY ','EP ','AT ','AC ','OC ','OH '/
```

That is **15 codes**, in this order: `PW`, `LW`, `FD`, `BG`, `HW`, `CW`, `PL`, `SE`, `BL`, `PY`, `EP`, `AT`,
`AC`, `OC`, `OH`. The count matches `PARAMETER (MAXSP =15)` in `canada/bc/PRGPRM.F77` line 12.

The same file gives two parallel code lists of 15 entries each: `FIAJSP` (FIA numeric codes, such as `119` for
`PW`) and `PLNJSP` (PLANTS symbols, such as `PIMO3` for `PW`). A fourth list, `NSP`, holds 45 names of the form
`PW1`, `PW2`, `PW3` through `OH1`, `OH2`, `OH3`, which is 15 species in three classes.

## The hazard this exposes

Three different tree-record formats are in play, and they are not the same:

| Source | Format |
| --- | --- |
| FVS-BC variant default, `canada/bc/blkdat.f` `TREFMT` | `I4,T1,I7,F6.0,I1,A3,F5.1,F4.1,2F5.1,F5.1,I1,3(I2,I2),2I1,I2,2I3,2I1,F3.0` |
| PyFVS default, `src/pyfvs/config_default.yaml` | `I4,T1,I8,F9.3,I1,A4,F5.1,F3.1,F3.0,F3.0,F2.1,I2,6I2,2I1,I2,2I3,2I1,F3.0` |
| PyFVS `keywords.py` doctest example | `I4,T1,I7,F6.0,I1,A3,F4.1,F3.1,2F3.0,F4.1,I1,3(I2,I2),2I1,I2,2I3,2I1,F3.0` |

PyFVS writes its own `TREEFMT` keyword when the caller's keyword set does not already contain one. From
`src/pyfvs/fvs.py`, around line 653:

```python
if <condition> and not keywords.find('TREEFMT'):
    keywords += kw.TREEFMT(self.treelist_fmt)
```

The species width differs between the BC default (`A3`) and the PyFVS default (`A4`), and the tree number,
tree count, and height fields differ as well.

Not verified, and this is the central question for `P2.2`:

- Whether PyFVS's injected `TREEFMT` reaches an `FVSbc` run, and whether it then misaligns a BC treelist.
- Whether `A3` against the four-character `JSP` entries matches as intended, or whether FVS pads or trims
  before comparing.
- What `NSP`'s three classes mean in output, and whether the contract must carry them.
- Whether the BC variant reads any tree-record field that `TREFMT` does not show, such as a variant name.

Until the spike answers these, the tree-list contract cannot be written from a format string alone.

## What this corrects

- `notes/scope.md` said the species handling was "keyed on the variant name". It is a flat list of 15 codes.
- The `ROADMAP.md` next-steps note pointed at `BC.trf` and "the species table", then at `bcspp.f`.
- The `P1` close-out report's recommendation pointed at `BC.trf`. It is closed evidence and is left as
  written; this note supersedes it.

Both earlier claims were plausible and wrong. Both were caught by reading the pinned source rather than a
summary of it.
